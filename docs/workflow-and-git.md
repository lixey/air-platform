## 1. Розподіл портів (IDE розробника проти ШІ-агента)

Щоб сесії розробника в JetBrains Rider / WebStorm та сервери, які запускає ШІ-агент для перевірки змін, ніколи не конфліктували за порти, `air-platform` використовує дві виділені пари портів:

| Середовище в `air-platform` (`demo`)           | Порт Бекенду (`Demo.Api`) | Порт Фронтенду (`demo/web`) |
| :--------------------------------------------- | :------------------------ | :-------------------------- |
| **Порти IDE розробника (Rider / WebStorm)**    | `5091`                    | `4300`                      |
| **Виділені порти ШІ-агента (`make agent-up`)** | `5191`                    | `4400`                      |

> Кожен окремий застосунок, побудований на базі платформи, визначає власну ізольовану пару портів IDE та Агента у своєму локальному `Makefile` та `AGENTS.md`.

- Запуск та перезапуск агентських серверів: `make agent-up`, `make agent-restart`.
- Зупинка агентських серверів: `make agent-down`.

## 3. Стандарти коду та `GlobalUsings.cs`

1. **1 тип = 1 файл:** Кожен `class`, `record`, `struct`, `interface` або `enum` має жити у власному `.cs` файлі, названому за іменем типу (для generic-перевантажень використовується суфікс `OfT`, наприклад `PlatformModuleOfTDefinition.cs`).
2. **Сувора структура папок:**
   - Усі DTO, запити та моделі контрактів (`*Dto`, `*Request`, `*Model`) — у папці `Contracts/`.
   - Усі `internal` класи — у папці `Internals/` (множина). Заборонено додавати `*.Internals` у `GlobalUsings.cs`.
   - Усі статичні класи з методами розширення (`this ...`) — із суфіксом `Extensions` (`*Extensions.cs`).
3. **Правило `PascalCase` для `Handle`:** Усі внутрішні ідентифікатори `Handle` (модулі, фічі, кольори, валюти, мови, провайдери ШІ) пишуться строго в `PascalCase` (`^[A-Z][a-zA-Z0-9]*$`, наприклад `App`, `Org`, `Ecom`, `Uah`, `Usd`). Для зовнішніх стандартів (ISO `UAH`, культура `uk-UA`, ідентифікатори CLI-моделей) використовується поле `Code` або `Id`.
4. **Проста англійська лексика:** Використовуйте прості, загальновживані англійські слова в назвах методів і класів (`RemoveUserAsync`, `ClearAsync` замість рідкісних слів на кшталт `EvictUserAsync`) і ніколи не жертвуйте читабельністю коду заради економії кількох рядків.

## 4. Правила Git-комітів

1. **Формат першого рядка (до 80 символів):**
   ```text
   <prefix>: <concise summary>
   ```
   Дозволені префікси `<prefix>`: `add:`, `upd:`, `del:`, `fix:`, `style:`, `chore:`.
2. **Мова комітів:**
   - У репозиторії `air-platform` повідомлення комітів пишуться виключно **англійською мовою (`en-US`)**.
3. **Чистота історії:**
   - Не змішуйте механічні перейменування/форматування (`upd:` із першим рядком тіла `mechanical`) та логічні зміни в одному коміті.
   - При зміні публічних контрактів платформи додавайте рядок `breaking: <what>, <who>, <what to do>`.
   - Жодних markdown-блоків (` ``` `), нерозривних пробілів або рядків `Co-Authored-By` у повідомленнях комітів (автоматично перевіряється `.githooks/commit-msg`).
