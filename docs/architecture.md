# Архітектура ядра: Дані (`Air.Data`) та API/Безпека (`Air.Api`)

Цей документ детально пояснює внутрішню будову двох фундаментальних шарів платформи: рівня даних (`Air.Data`, `Air.Data.Postgres`, `Air.Data.SqlServer`) та рівня модульного API-хоста (`Air.Api`).

---

## Частина 1. Рівень даних (`Air.Data`)

Проєкт `Air.Data` (простір імен `Platform.Data.*`) побудований на **EF Core 10** і свідомо не має жодної залежності від ASP.NET Core або вебшару. Завдяки цьому його можна використовувати в CLI-утилітах міграцій, фонових воркерах, інструментах перенесення даних (`Bcc.Transfer`) та тестах.

### 1.1. Ієрахія базових сутностей (`Platform.Data.Entities`)

Усі таблиці в платформі та прикладних модулях успадковують один із канонічних базових класів або інтерфейсів:

### 1.2. `PlatformDbContext`: мульти-тенантність, конвенції та захист даних

`PlatformDbContext` автоматизує рутинні правила роботи з БД:

1. **Автоматичні глобальні фільтри тенанта (`Query Filters`):**
   - Для кожної сутності `IHasTenant` автоматично накладається фільтр за поточним `TenantContext.TenantId`.
   - Якщо сутність реалізує `IInheritedByChildTenants`, запит повертає рядки поточного тенанта (`TenantId == currentTenantId`) **або** глобальні рядки (`TenantId == null`).
   - При збереженні (`ApplyEntityConventions`) `PlatformDbContext` автоматично проставляє `TenantId` для нових записів і блокує будь-які спроби звичайного тенанта змінити `TenantId` або відредагувати/видалити глобальний рядок (`TenantId == null`), якщо не активовано системний скоуп (`TenantContext.IsSystemScope`).
2. **Оптимістична конкуренція (`Ver`) та штампи часу:**
   - При кожному `Modified` поле `Ver` автоматично збільшується на `1` (один раз за межі `MutationRun`), а `UpdatedAt` оновлюється поточним UTC-часом.
3. **Канонічне правило зовнішніх ключів (`DeleteBehavior.Restrict`):**
   - За замовчуванням для всіх зовнішніх ключів у `PlatformDbContext` встановлюється `DeleteBehavior.Restrict` (окрім явно заданих `OnDelete(DeleteBehavior.Cascade)` у конфігурації сутності), що унеможливлює випадкове каскадне знищення пов'язаних бізнес-даних.

### 1.3. Модульна ізоляція схем та міграцій (`[ModuleSchema]`, `ModuleOwnershipConvention`)

Згідно з **ADR #8**, кожен модуль має власний самодостатній `*DbContext`, який успадковує контекст базового модуля:
`PlatformDbContext` → `AppDbContext` → `OrgDbContext` → `EcomDbContext`.

Як платформа розуміє, якому модулю належить кожна таблиця в такій ієрархії?

- Кожен модуль позначає свій `DbContext` та/або збірку `*.Data` атрибутом `[ModuleSchema("ecom")]` (або `[assembly: ModuleSchema("ecom")]`).
- **`ModuleOwnershipConvention`** автоматично визначає модуль-власник кожної сутності за її збіркою (`TEntity.Assembly`). Якщо сутність не належить поточному модулю (наприклад, успадкована з `AppDbContext` або позичена з сусіднього модуля через `DbSet<TEntity>`), конвенція автоматично викликає `entityType.SetIsTableExcludedFromMigrations(true)` для поточного модуля!
- Якщо розробник забув вказати `[ModuleSchema]` для нової сутності поза `Air.Data`, `ModuleOwnershipConvention` миттєво викине зрозумілий `InvalidOperationException` (fail-fast).
- Історія міграцій зберігається в єдиній таблиці `__PlatformMigrations` (`PlatformMigrationHistoryRepository`) із колонкою `Module`, тому міграції кожного модуля виконуються ізольовано й ніколи не конфліктують між собою.

### 1.4. Автоматичний журнал аудиту (`AppPlatformChange`)

`PlatformDbContext` автоматично записує історію всіх створень, змін і видалень сутностей у таблицю `AppPlatformChange` (крім сутностей, позначених `[NoAudit]`, або операцій усередині `db.SuppressAuditScope()`, як-от стартовий сидинг `CodeRows.SyncAsync`):

- **Атомарність запису:** У методах `SaveChanges` / `SaveChangesAsync` дані та рядки журналу `AppPlatformChange` записуються в одній транзакції з `acceptAllChangesOnSuccess: false`. `ChangeTracker.AcceptAllChanges()` викликається лише **після** успішного коміту транзакції, що гарантує повну консистентність при повторах `ExecutionStrategy`.
- **Консолідація в межах `MutationRun`:** Якщо під час однієї бізнес-мутації (`MutationRunner`) сервіс робить кілька проміжних `SaveChangesAsync()` (наприклад, створив замовлення, додав рядки, перерахував підсумки), `PlatformDbContext` об'єднує їх в **один фінальний запис аудиту** на кожну сутність із точним фінальним знімком `After`.
- **Відокремлення похідних перерахунків (`IsDerived`):** Коли після основної дії користувача запускаються каскадні правила (`RunDerivedRecalculationAsync`), перед перерахунком основні зміни фіксуються в журналі як пряма дія користувача, а похідні зміни батьківських агрегатів позначаються прапорцем `IsDerived = true`.

### 1.5. Песимістичні блокування (`LockAsync`)

Для захисту критичних фінансових і складських операцій (проведення документів, списання партій, переходи статусів) від гонитви потоків платформа надає універсальний механізм песимістичних блокувань:

- **PostgreSQL (`Air.Data.Postgres`):** встановлює `SET LOCAL lock_timeout = '15s'` і виконує `SELECT ... FOR UPDATE` / `pg_advisory_xact_lock`.
- **SQL Server (`Air.Data.SqlServer`):** використовує `SET LOCK_TIMEOUT 15000` та табличні хінти `WITH (UPDLOCK, ROWLOCK)` / `sp_getapplock`.

### 1.6. Декларативний рушій запитів (`DataProvider<TEntity, TRow>` та `QueryMap`)

Папка `Air.Data/Querying` реалізує трансляцію клієнтських запитів таблиць (`GridRequest`: пошук, фільтри, сортування, пагінація, агрегації) безпосередньо в дерева виразів EF Core (`Expression<Func<TEntity, bool>>`):

- **`QueryMap<TEntity, TRow>`** автоматично будує мапінг між шляхами колонок клієнта (`camelCase`) та властивостями сутності `TEntity` (або проєкції `TRow`), враховуючи прапорці `.Sortable(false)` та `.Filterable(false)`.
- **Розумний пошук (`SearchPredicateBuilder`):** розбирає пошуковий рядок користувача (підтримує числові префікси `=100`, `>50`, діапазони, текстові токени та пошук за пов'язаними довідниками).
- **Підрахунок сум (`Sum`):** обчислює підсумки за числовими колонками на стороні СУБД одним агрегатним запитом паралельно з вибіркою сторінки.

## Частина 2. Безголовий модульний API-хост (`Air.Api`)

Проєкт `Air.Api` (`Platform.Api.*`) відповідає за модульну структуру, автентифікацію, авторизацію (RBAC), мутації, файли та HTTP-конвеєр.

### 2.1. Модулі, `Feature` та `Right`

Кожен бізнес-модуль (наприклад, `BccOrg` або `MyFin`) складається з:

1. **Опису фіч (`<Mod>.cs`)**:
   ```csharp
   public static class Fin
   {
     public const string Handle = "Fin";
     public static readonly Feature Expense = new(Handle, nameof(Expense));
     public static readonly Feature Account = new(Handle, nameof(Account));
   }
   ```
   Кожна стандартна `Feature` автоматично має базові права:
   - `Feature.View` (`Fin.Expense.view`) — перегляд записів і форми;
   - `Feature.MenuView` (`Fin.Expense.menu`) — відображення пункту в головному навігаційному меню;
   - `Feature.Edit` (`Fin.Expense.edit`) — створення та редагування;
   - `Feature.Delete` (`Fin.Expense.delete`) — видалення;
   - `Feature.Export` (`Fin.Expense.export`) — експорт у Excel.
     Для тонких обмежень даних використовується `Feature<TAccess>` (наприклад, `Feature<OrderAccess>`), де `OrderAccess : FeatureAccess` оголошує додаткові права контейнера (`access:...`).
2. **Класу модуля (`<Mod>Module : PlatformModule<TDbContext>`)**: реєструє `DbContext`, ресурси локалізації та сервіси модуля в `ModuleCatalog`.

### 2.2. Канонічна модель прав доступу (RBAC) та безпека

Усі перевірки прав у платформі працюють за принципом **fail-closed** (якщо користувач не автентифікований — доступ заборонено) та використовують єдині канонічні формули в `ServiceEndpointsExtensions`:

- **`CanView(feature, user)`**: `user.IsAuthenticated && (user.Can(feature.View) || user.Can(feature.Edit))` (маски `*`, `Module.*`, `Module.Feature.*` автоматично розпізнаються в `HeldRights.Covers`).
- **Видимість у меню (`MetadataEndpoints`)**: `CanView(feature, user) && user.Can(feature.MenuView)`. Таким чином, право `MenuView` керує лише видимістю пункту в меню, але ніколи не відкриває доступ до даних без `View` або `Edit`.
- **`CanEdit(feature, user)`**: `!feature.IsReadOnly && user.IsAuthenticated && user.Can(feature.Edit)`.
- **`CanDelete(feature, user)`**: `!feature.IsReadOnly && user.IsAuthenticated && user.Can(feature.Delete)`.

#### Захист від ескалації привілеїв при керуванні користувачами та ролями:

- **`CoversUserGrantsAsync` та `CoversRoleGrantsAsync` (`PlatformAppService`)**: Адміністратор не може редагувати/видаляти користувача чи роль, які мають ширші права або ширший тенантний охоплення (`Scope`), ніж він сам. Не-root користувач ніколи не може редагувати `IsRoot`-користувача.
- **`IsRoot`-користувач**: зберігає повні права (`*`) навіть під час перемикання сесії в дочірній тенант.
- **Захист останньої адмін-ролі**: Пакетне видалення ролей перевіряє, що після видалення всього вибраного пакета (`ctx.Ids`) у кожному зачепленому тенанті залишається щонайменше одна активна роль із повними правами `*`.

### 2.3. Автентифікація та сесії (`AuthEndpointsExtensions`)

- Використовується двотокенна схема в `HttpOnly` cookies (`SameSite = Lax`): короткоживучий підписаний `AccessCookie` (30 хв) та ротований `RefreshCookie` (30 днів) із детекцією повторного використання (`reuse` grace-вікно 30 сек для конкурентних вкладок).
- **Захист логіну:** Експоненціальний lockout після 5 невдалих спроб (`429 TooManyRequests`) та холоста перевірка хешу (`DummyPasswordHash`) при неіснуючому логіні для захисту від таймінг-атак.
- **Захист від CSRF:** Усі мутуючі POST-запити (включно з `/auth/refresh`, `/auth/logout`, `/platform-language/switch`, `/platform-tenant/switch`) вимагають заголовок `X-Platform-Client`.
- **Кеш авторизації (`IUserAuthCache`):** Миттєво інвалідується при зміні пароля, деактивації користувача, зміні ролей або відкликанні сесій (`RevokeUserSessionsAsync`).

### 2.4. Конвеєр мутацій (`MutationRunner`) та ідемпотентність

Усі операції запису (`Save`, `SaveCell`, `Delete`, `MoveStatus`, кастомні дії) виконуються через `MutationRunner`:

- Відкриває транзакцію та область `MutationRun` у `PlatformDbContext`.
- Забезпечує **ідемпотентність створення (`RunIdempotentCreateAsync`)** за ключем клієнта (`IdempotencyStore` з лімітом довжини ключа та розміру кешу): повторний запит із тим самим ключем ніколи не створить дублікат запису.
- Перехоплює конфлікти конкуренції (`DbUpdateConcurrencyException`) та бізнес-відмови, повертаючи структурований `MutationResultDto` (`Committed`, `Refused`, `Conflict`).

### 2.5. Стійка серіалізація JSON (`PlatformJsonOptions`)

- Для nullable числових типів (`long?`, `int?`, `decimal?`) порожній рядок `""` та `null` десеріалізуються строго в `null` (`ResilientNullable*Converter`), щоб необов'язкові зовнішні ключі (FK) ніколи не отримували `0`.
- Для non-nullable чисел (`long`, `int`, `decimal`) порожній рядок `""` безпечно приводиться до `0`.
- Конвертери дат (`ResilientDateTimeConverter`, `ResilientNullableDateTimeConverter`) використовують `TryGetDateTime` та `DateTimeStyles.None` (зберігають календарну дату без небажаного зсуву часового поясу при парсингу та повертають коректну помилку валідації замість HTTP 500 на невалідному рядку).
