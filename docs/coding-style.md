# Канон коду C# 14, виразів (`Expressions`) та розумного тестування

Цей посібник визначає єдиний стиль написання коду в ядрі платформи (`src/`, `air-ui/`) та прикладних модулях (зокрема еталонному `demo/`). Головний принцип: **код пишеться лаконічно й сучасно (рівень найкращої інженерної практики C# 14), але без «заумності» — так, щоб будь-який розробник чи архітектор прочитав і зрозумів файл за 30 секунд**.

---

## 1. Ідіоми C# 14 та сучасного .NET 10 (Що й де застосовувати)

1. **Первинні конструктори (`Primary Constructors`)**:
   - Використовуйте у всіх сервісах, провайдерах і внутрішніх хелперах замість дублювання приватних полів і конструктора:
     ```csharp
     public sealed class ProductFormService(OrgDbContext db, OrgService app)
       : OrgFormService<Product>(db, app)
     ```
2. **Ключове слово `field` (C# 14)**:
   - Використовуйте для лінивої ініціалізації або нормалізації властивостей замість ручних полів `_backingField`:
     ```csharp
     public TimeProvider Time => field ??= new ScopedTimeProvider(
       Services.GetService<TimeProvider>() ?? TimeProvider.System,
       TimeZoneInfo.Utc);
     ```
3. **Колекційні вирази (`Collection Expressions`: `[]`, `[.. items]`)**:
   - Використовуйте `[]` замість `new List<T>()` / `Array.Empty<T>()` та `[.. query]` замість зайвих `.ToList()` / `.ToArray()`, коли потрібні компактні знімки колекцій:
     ```csharp
     public override IReadOnlyList<ModuleDoc> Docs =>
     [
       new("Ecom Trade & Warehouse Workflows", DomainKnowledge)
     ];
     ```
4. **Строго типізовані дерева виразів (`Expression<Func<TEntity, TProp>>`)**:
   - Усі колонки таблиць, поля форм, правила валідації, реактивні патчі (`PatchOnSelect`), підсумки дочірніх рядків (`SumTo`), фільтри довідників (`FilterBy`) та захист видалення (`PreventDeleteWhenUsedBy`) описуються **виключно через типізовані лямбда-вирази**, а не рядкові назви властивостей:
     ```csharp
     elements.Add(e => e.ProductId)
       .AsReference<ProductGridService>(p => p.Name, p => p.Code)
       .PatchOnSelect<Product>(p => p.SalePrice, e => e.Price);

     hooks.PreventDeleteWhenUsedBy<EcomDocLine>(l => l.ProductId);
     ```
   - Це дає 100% перевірку під час компіляції, миттєву навігацію в IDE та безпечну побудову SQL-запитів через EF Core без Dynamic LINQ.
5. **Зіставлення зі зразком (`Pattern Matching`) та `switch`-вирази**:
   - Віддавайте перевагу декларативним зразкам властивостей та списків (`is null or { IsActive: false }`, `is [var first, ..]`) і вичерпним `switch`-виразам замість каскадів `if / else if`:
     ```csharp
     if (user is null or { IsAuthenticated: false })
     {
       return false;
     }
     ```
6. **`sealed` за замовчуванням та `record` для незмінних моделей**:
   - Кожен кінцевий сервіс, хелпер чи реалізація позначається `sealed`.
   - Контракти даних, конфігураційні дескриптори та події без мутації описуються як `public sealed record`.

## 2. Табу проти «заумного» коду (Anti-Cleverness Rules)

Лаконічність ніколи не повинна перетворюватися на ребус:

- **Жодних вкладених тернарних операторів** (`a ? b : c ? d : e`) — замініть на `switch`-вираз або ранні перевірки (`if (...) return ...;`).
- **Жодних 15-рядкових ланцюжків LINQ із вкладеними кортежами** — розбивайте складний запит на іменовані проміжні змінні з очевидним змістом.
- **Проста щоденна англійська лексика**: використовуйте базові прозорі слова (`Remove`, `Clear`, `Load`, `Build`, `Bind`, `Check`) замість рідкісних академічних термінів (`Evict`, `Coalesce`, `Hydrate`, `Reify`).
- **Жодної рефлексії чи магії рядків у прикладному коді**: рефлексія та компіляція дерев виразів дозволені лише всередині інфраструктурних кешів ядра (`Internals/`), але ніколи в прикладних модулях.
- **Заборонені конструкції контролюються компілятором (`BannedSymbols.txt`, `RS0030`)**: прямі виклики `DateTime.Now`, `DateTime.UtcNow`, `DateTimeOffset.Now`, `DateTimeOffset.UtcNow`, `MD5`, `SHA1`, `FromSqlRaw`, `SetIsOriginAllowed`, `AllowAnyOrigin` ламають збірку на етапі компіляції. Для часу використовуйте виключно `app.Time` або `TimeProvider`.

## 3. Анатомія файлу прикладного сервісу (Читання за 30 секунд)

Кожен сервіс фічі мешкає у власному файлі (`1 тип = 1 файл`) і дотримується незмінного порядку секцій зверху вниз:

1. `public override Feature Feature => ...;` — явна прив'язка до фічі та прав RBAC.
2. Опис структури екрана (`SetColumns` / `SetElements` / `SetStates` / `BuildLayout`) — без побічних ефектів у БД.
3. Запит та іменовані фільтри (`Query`, `SetNamedFilters`).
4. Декларативні правила та життєвий цикл запису (`SetRules`, `SetHooks`, `BeforeSave`, `AfterSave`).
5. Дії користувача (`SetActions`).

Не перевизначайте `Presentation` вручну, якщо автоматичне правило платформи (`<= 8` видимих скалярних полів → `Popover`, інакше → `Drawer`) вже дає потрібний результат.

## 4. Стандарт розумного тестування критичних шляхів (Smart Critical-Path Testing)

Ми не пишемо церемоніальні тести «на кожен чих» (на прості декларативні довідники чи порожні DTO), але **залізобетонно покриваємо швидкими детермінованими тестами всі критичні вузли**:

1. **У платформі (`tests/`) — обов'язкові тести**:
   - **`Air.ArchTests`**: механічні закони архітектури (граф залежностей збірок, чистота шарів без витоку логіки агента в ядро, `1 тип = 1 файл`, маркування секретів `[Sensitive]`, реєстрація культур і паритет `.resx`).
   - **Безпека, RBAC та ізоляція тенантів**: перевірка `CanView`/`CanEdit`/`CanLookup`, захист `IsRoot`, делегування прав, сесії та куки.
   - **Рушій запитів, форм і мутацій**: фільтрація, сортування, `PatchOnSelect`, `SumTo`, правила `Error`/`Warning`, статусні переходи та ідемпотентність.
   - **Безпека та контракти ШІ-асистента**: побудова та виконання `<ui_proposal>`, ізоляція пам'яті та захист від ін'єкцій.
2. **У прикладних системах (`demo/` та бізнес-застосунках) — обов'язкові тести бізнес-логіки**:
   - Розрахунки сум, знижок, податків, курсових різниць і залишків (склад, гроші, взаєморозрахунки).
   - Проведення документів, переходи статусів (`StatusFlowService`) і побічні рухи (`AddFollower`).
   - Імпорт, синхронізація виписок і звірка даних (`reconcile`).
   - Прості CRUD-екрани без кастомних обчислень повторно тестувати не потрібно — їхню роботу вже гарантують тести ядра платформи та компілятор.
